# Full-stack audit — 2026-07-27

Scope: convex schema + backend, Next.js API routes, chrome extension contract, frontend components. Four parallel deep-dives, findings deduplicated and spot-verified. Severity reflects real-world impact for a single-owner vault that is publicly deployed.

Verified by hand before publishing: `users.normalizeOwnership` is public and authless; `validateExtensionToken` fails open and `.env.local` sets the wrong env name (`EXTENSION_API_KEY` vs the `EXTENSION_API_TOKEN` the code reads); `moveAssetsToFolder` → `setAssetFolders` replace semantics; `getAsset` returns-validator omissions.

## 1. Security exposure

The root problem: **there is no `ctx.auth` anywhere in `convex/`**. Every Convex function is publicly callable with a caller-supplied `ownerUserId`, and `NEXT_PUBLIC_CONVEX_URL` ships in the browser bundle. Every ownership check in `app/api/**` is advisory. Specific endpoints that are dangerous even knowing that:

| Sev | Where | Problem |
|---|---|---|
| critical | `convex/users.ts:124` `normalizeOwnership` | Public authless mutation that rewrites `ownerUserId` on every asset, prompt, user, and run to a caller-supplied string. Total takeover in one call. Also dead code — zero callers. Delete it. |
| critical | `lib/server/extension-auth.ts:29` + `.env.local:43` | `validateExtensionToken` returns `true` when `EXTENSION_API_TOKEN` is unset — and it IS unset (env sets `EXTENSION_API_KEY`, a name the code never reads; the extension itself sends no token at all). | high | `convex/removeSauceAssets.ts:32` | Public action that deletes every asset with `modelName === "sauce"`, no auth. One-off migration long done. Delete the file. |

## 3. Storage-model problems ("a more proper storage system")

### 3.1 Membership: finish the migration you already decided on

`assetFolders` is the declared source of truth; `assets.folderId` is a legacy alias — but **three write conventions coexist** (`assets.ts` maintains the alias, `projects.ts` writes links only, `updateAssetMetadata` full-replaces it) and reads split three ways (§2). The `membershipAudit` invariant is enforced only by a manually-run mutation. Direction: funnel every membership write through one helper in `folderHelpers.ts`, run the audit, then make `folderId` read-only (or drop it behind a shim).

Same story twice more:
- **Tags**: `assets.tagIds` array + `assetTags` join, both maintained; filtering reads the array, counting reads the join. Repeated for prompts and designInspirations. The join is the only shape indexable by tag; the arrays have no owner scope.
- **Beat links**: `projectCollections.beatCharacter/LocationFolderId` legacy singles alongside the arrays (`schema.ts:168-171`). Reads merge, writes clear singles. Backfill once, drop two columns.

### 3.2 Counts: denormalize instead of scanning

The dashboard subscribes to four queries that scan large tables on **every asset write**:
- `folderAssetCounts` (`assets.ts:2914`) — two unbounded collects per folder × owner candidates.
- `galleryAssetFacets` (`assets.ts:1520`) — collects every owner asset to return `{totalCount, modelCounts}`; with `{}` it's an authless full-table scan of the biggest table.
- `listPublicCollections` (`assets.ts:2987`) — collects all public assets, then one `assetFolders` query **per asset** (textbook N+1), public + authless.
- `listProjects` (`projects.ts:146`) — walks every member collection's full link set per project for a count.

Also: `userTags.collectOwnerTagUsage` recollects all assets+prompts+designs per call (usageCount already exists); `showcase.getShowcaseHome` pulls up to 200 assets per showcased folder + per sub-collection, authless; `listCollectionSummaries` collects the entire `tags` table because `tags.normalized` uses a different normalization (`normalizeTagName`) than lookups need (`canonicalTagKey`) — store `canonicalKey` as an indexed column.

Direction: a `memberCount` (and `publicMemberCount`) on `folders`, bumped in the membership helper from 3.1, kills the first four. Extend the wrapped-cursor pagination (already built for newest-sort) to tag filters and other sorts instead of the silent 600-cap one-shot (`dashboard.tsx:1650,1784,1836` — the sidebar meanwhile shows the true total, so "900" next to a grid that can never show more than 600).

### 3.3 `folders` overload

Four kinds (`undefined` | storybook | project | direction) + 9 kind-specific optional flags on one table, with kind rules enforced ad hoc or not at all:
- `description` means description / story text / project brief depending on kind, and the DTOs rename it (`story`, `brief`).
- `coverAssetId` and `pinnedAt` are per-**folder** but the product semantics are per-**project-workspace** — a recurring character direction pinned in one project is pinned in all of them. `section` got it right by living on the join row; move these there too. Same one level down: `assets.orderPriority`/`pinnedAt` are global but described as "in the project workspace" — belongs on `assetFolders`.
- `folders.listFolders` is exposed unfiltered to agent/API pickers (`app/api/folders`, `agent/gallery`, `agent/customize`) — projects, storybooks, and every auto-created "— Inbox" direction appear as if they were collections. Only the extension routes filter. Make kind-filtering server-side and default.
- `menuFilters` accepts storybooks as "collection" pills (`menuFilters.ts:259` + admin picker) — decide and make validator + picker agree.
- No `by_owner_kind` index — five call sites fetch all owner folders and filter in JS.

### 3.4 Loose typing worth tightening

- `pillarValidator = v.string()` (`validators.ts:3`) — free text used as an index key and a vector-index filter field; a typo silently creates an empty search scope.
- `promptProfileValidator` uses `pillar: v.literal("creators"|"designs"|"dump")` as the **discriminant** of a live union — the retired taxonomy is load-bearing in a currently-written column. Re-discriminate on promptType/kind.
- `semanticDocuments.sourceId: v.string()` — stringified FK next to three typed id columns for the same row, cast back with `as Id<…>`.
- `runs` all-optional because of one rogue `RunMusic` doc the schema comment admits should just be deleted; duplicate union literals (`creator_assist` ×2, `canvas` ×2).
- `ownerUserId` optional on assets/folders — an owner-less row is unreachable through all 12 `by_owner_*` indexes. Backfill + require.
- `boardReactions` "exactly one of assetId/folderId" is a comment, not a type.
- `tags` has no `ownerUserId` and a global `usageCount` — the known correctness hole `menuFilters.ts:131` documents; duplicate tag docs already forced `mergeDuplicateTags.ts` into existence.
- Four `v.any()` blobs (`ingest_failures.payload`, `runs.input`, `run_events.payload`, `run_artifacts.metadata`); at least discriminate the last two on their existing `type`/`mode` unions.
- `section` validator has four layers ("stills") but the schema comment documents three.

### 3.5 Index hygiene

~16 indexes with zero `withIndex` callers (list in the schema agent's findings; includes all `by_*pillar*` composites, `folders.by_name`, `users.by_email`, four designInspirations composites, `runs.by_status_createdAt`). Each is write amplification on hot tables. Add the one index that's actually missing (`folders.by_owner_kind…`), delete the rest.

## 5. Backend structure (duplication, contracts)

- **Five** implementations of "normalize tag name → find-or-create" (each with a full `tags` collect); **seven** inline copies of the preview-asset projection; **five** copies of "collect owner folders by kind"; **four** copies of the asset index-selection ladder + post-filter in `assets.ts`; **three** verbatim copies of the curator guard next to the existing `assertCurationAdmin`; ownership guards written four ways with four error strings; `searchAssets`/`findSimilarAssets` share ~80 duplicated lines. Each wants one shared helper.
- Six different "an asset" return shapes across `getAsset` / `getGalleryAsset` / `listAssets` / `listGalleryAssets` / packs / showcase — raw doc (leaks `ingestKey`, lacks `url`) vs hydrated vs trimmed. Standardize on `galleryAssetResultValidator` + one explicit public/trimmed variant.

## 7. UX naming (visible copy)

- One folder entity is called **beat**, **direction**, and **stack** on the same review screen ("Delete this beat" / "Delete this direction" / "Upload files into this stack"), plus "board" for the shared view. Pick the vocabulary and sweep the strings (`POOL_LABELS`/`TAB_LABELS` show the pattern).
- "folder" leaks into user-facing error copy (~8 sites in dashboard) while the product says "collection".
- "Storybooks" is a boolean bolted beside `ViewMode` instead of a fourth mode — it can be true while `viewMode === "packs"`.
- Two "clear" buttons with different scopes and near-identical labels ("Clear all" vs "CLEAR ALL FILTERS"), one of which doesn't clear search (§2).
- `tasteCollection` boolean is named like a per-owner setting but indexed like a global singleton.
- Product-word → schema-predicate mapping is tribal knowledge ("stack" = showcased folder, "board" = project with shareToken, "direction" = kind OR any collection with a cover…). Add a glossary comment atop the `folders` definition.

## 8. Recommended attack order

1. **Security purge (small diff, biggest risk cut)** — delete `normalizeOwnership`, `removeSauceAssets.ts`, `r2_migrate*.ts`, `mergeDuplicateTags.ts`, `backfillDimensions.ts`; fix the extension token env name + fail-closed + CORS; add `serverSecret` to `runs.ts`; owner-scope `assetPacks` + showcase indexes; guard the telegram webhook and dev simulate routes.
2. **Data-loss fixes** — drag-drop additive everywhere (Move stays an explicit toggle), stop `replaceAssetFolderLinks` behind single-folder edits, `allowedKinds` in `ensureFolderOwnership`, refuse kind mutation in `createFolder`, fix the three returns validators, backfill `normalizedName`, route bulk deletes through `internalDeleteAsset`.
3. **Storage-model consolidation** — one membership-write helper; links-only reads; denormalized `memberCount`; drop `assets.folderId` + beat singles after backfill; `canonicalKey` column on tags; `by_owner_kind` index + delete the ~16 unused ones.
4. **Dead-code sweep** — pillars (decide restore-vs-delete for `selectedPillar` first), direction-board + canvas cluster, dead routes, dead Convex exports, backend-review page, docs drift. Roughly 10k+ lines out.
5. **Frontend decomposition** — conditional-mount the modals, single detail panel, navigation reducer + contexts, escape/z-index/modal primitives, image strategy, naming sweep.

Items 1–2 are shippable independently and fast. Item 3 unlocks 4 of the 5 worst live queries. Items 4–5 are quality-of-life but item 4's pillar decision blocks parts of item 5.
