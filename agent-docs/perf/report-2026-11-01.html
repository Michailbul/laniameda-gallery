Not built

Grid virtualisation

Native lazy loading already keeps far tiles from downloading, and .card-base's content-visibility already bounds style and paint. Unmounting tiles would add marquee and re-entry complexity for no download saving.

Live /, 390x844 at DPR 3, cache off, focus emulated, no eager forcing: at load 36 tiles mounted, 27 of them more than 1.5 screens below the fold, 3 of those 27 downloaded. After 10 screens of scrolling: 72 tiles, 5,816 DOM nodes, 63 image requests. The 31 Oct refuter's 4x-CPU scroll showed the same frame-time distribution at 37 and 109 mounted tiles.

Live

Sidebar data after the grid

On home the folder tree, folder counts, tag vocabulary, saved views and the inbox/task badges now subscribe after the grid's first page is in, and skills and storybooks travel slimmer. A world address still loads the folder tree first, because it picks the world's grid from it.

First websocket frame on / (raw JSON): 864,626 B before, 407,903 B after; it still carries the grid page (149,788 B), the shelf (54,629 B) and the skill cards (195,186 B). The support frame follows 0.45 s later unthrottled. /w/dear-annete first frame: 1,003,912 B (31 Oct) to 624,138 B.

480/960 renditions for shelf previews

The repo's own sharp backfill now takes a list of asset ids, so it ran on the shelf previews alone instead of rewriting 4,867 thumbs across the vault. No paid image service is involved.

40 of 63 shelf preview images lacked renditions; thumbnails:backfillCardThumbnails {assetIds} rebuilt 40, failed 0. A full-table dry run lists 4,867 candidates; that wider pass was left alone.

Written down

Folder descriptions stay in the tree

Descriptions are 111 KB of the 210 KB folder tree, but the Add-to drawer edits them from that list, so a cut-down copy could save a truncated description. On home the tree is no longer in the first frame; on a world address it costs about 35 KB on the wire.

folders:listFolders, 259 rows: description 110,931 B of 209,415 B raw. Editor: add-to-panel DescriptionEditor seeded from the folder list.

Next

Home LCP is the data chain, not the image

The largest paint on / and /w is the first grid tile. It already loads eager with fetchpriority=high, but the browser only learns its URL after the JS, the sign-in check and the first Convex frame. Server-rendering the first row of tiles (or preloading their 480w URLs from the server) is the next lever. That is an architecture change, so this thread stopped short of it.

Lighthouse mobile / after #123, median run: LCP 7.2 s, of which resource load delay 1,580 ms and load duration 130 ms (lcp-breakdown); 'request discoverable in initial document: false'. Signed-out / (no Convex wait): LCP 1.1 s.

/tasks changed into the review wall after 30 Oct and now carries 1.4 MB of images. Its wall shifts once as it fills. It is outside this thread (no speed PR touched it) and needs its own fix: reserved heights for the wall strip.

Next

Folder tree re-sent on every agent save

While an agent was saving, listFolders (210 KB) and folderAssetCounts were re-sent with each grid re-emit, about every 2.5 s. Filing an asset patches the denormalized folders.memberCount (recountFolderMembers), which changes the folder list. Serving counts apart from the tree (the UI already has folderAssetCounts) would stop the re-send.

Live /, LTE + 4x CPU, 1 Nov 20:55: frames at 4.7, 7.2 and 9.8 s each 378-381 KB, carrying folders:listFolders 210,182 B and assets:folderAssetCounts 15,298 B.
